# 线上监控统计 — 设计方案

> 状态:设计中(未实施) · 分支:localcoding-mvp · 日期:2026-06-23

## 1. 背景与目标

为正式打包的安装包(release)接入一套线上监控统计,覆盖崩溃、错误、使用行为、基础性能四个维度,数据上报到自建后端。

其中**核心使用指标**为「每日消息发送数」与「每日活跃设备数(发消息人数)」,详见 §7.1。

核心约束:

- **只对打包安装包外发**:开发调试态(`pnpm electron:dev`)**不向阿里云外发**任何数据。但为便于开发期排查,dev 态会把 telemetry 事件**本地记录到 server 日志**(`server-YYYY-MM-DD.log`,需 `LOCALCLAW_LOG_FILE=1`),不发网络请求。详见 §6.5。
- **唯一判别源**:Electron 主进程的 `app.isPackaged`,向下游扩散,不依赖 `NODE_ENV`(见 §2)。
- **匿名设备 ID**:生成并持久化一个匿名标识,用于区分独立设备数与留存,不含任何 PII。
- **用户可见开关**:设置项里提供「关闭使用统计」,关闭后立即停止上报。
- **上报后端**:阿里云 SLS WebTracking(免鉴权打点),完整 track URL 经环境变量 `APP_TELEMETRY_URL` 下发,代码不写死。地址已确定:`https://localcoding.cn-beijing.log.aliyuncs.com/logstores/localcoding/track`。详见 §6.2。

## 2. 环境判别(release vs dev)

### 2.1 为什么不能用 NODE_ENV

- 前端 bundle:`scripts/build-frontend.cjs` 把 `process.env.NODE_ENV` 永远写死为 `"production"`。
- server fork:`electron/main.cjs` fork 时永远传 `NODE_ENV: "production"`。

所以 dev 与 release 的 `NODE_ENV` 完全相同,**不可用作判别**。

### 2.2 唯一真相源:app.isPackaged

`electron/main.cjs` 已在使用 `app.isPackaged`;`scripts/electron-dev.cjs` 显式删除 `ELECTRON_FORCE_IS_PACKAGED`,dev 不会被误判为 release。判别信号向三个运行时扩散:

```
electron/main.cjs (app.isPackaged) —— 唯一真相源
  ├─→ fork server 时注入 env:
  │     APP_IS_PACKAGED = "1" | "0"
  │     APP_VERSION     = app.getVersion()
  │     APP_PLATFORM    = process.platform
  │     APP_INSTANCE_ID = <持久化匿名ID>
  ├─→ 主进程 telemetry 直接读 app.isPackaged
  └─→ preload.cjs 暴露 window.electronAPI.appInfo(前端首选)
```

环境变量使用 `APP_` 前缀(产品无关),避免硬编码品牌名到底层逻辑。

server 侧加 `config/release.ts` 提供 `isRelease()`(读 `APP_IS_PACKAGED === "1"`);前端经 preload 拿,external-server 远程部署场景用 `GET /api/app-info` 兜底。

## 3. 整体架构

三个运行时(主进程 / Node server / 前端)都不直连上报后端,**统一经本地 server 中转**:

```
前端 (React)        ┐
主进程 (main.cjs)   ┴──→ POST http://127.0.0.1:10086/api/telemetry (本地)
                          └─→ server 缓冲/批量/补公共字段/拍平
                                └─→ POST https://{project}.{region}.log.aliyuncs.com
                                          /logstores/{logstore}/track  (SLS WebTracking)
```

经 server 中转的理由:

- 上报后端地址、密钥只在 server 一处,不进前端 bundle(F12 即可见)。
- server 统一补公共字段(version / platform / instanceId / 时间戳),并把信封**拍平**成 SLS 扁平 KV(§6.2)。
- 失败/离线时 server 端落盘重试(复用 `~/.localcoding/logs` 落盘先例)。
- 关闭开关由 server 统一执行:关闭后本地 `/api/telemetry` 直接丢弃,不外发。

## 4. 匿名设备 ID

- 首次启动生成 UUID v4,持久化到 `app.getPath("userData")/telemetry-id.json`(**最终落点**,与配置解耦,重置时不影响其他设置)。
- 仅含随机 ID,**不含**机器名、MAC、用户名等任何可定位信息。
- 主进程读取后经 env `APP_INSTANCE_ID` 注入 server,作为上报公共字段。
- 用户「重置统计标识」时可删除重建(可选,后置)。

## 5. 用户可见开关

- 设置面板新增「发送匿名使用统计」开关,默认**开启**(release 态)。
- 状态持久化到 agent-settings(复用 `@lenovo/agent-sdk` 的 settings),server 端读取。
- 关闭后:server 收到本地上报立即丢弃,不外发;前端可停止采集。
- 首次启动给一次非阻塞知情提示(toast/小卡片),符合隐私合规预期。

## 6. 上报协议

### 6.1 内部信封(三端 → 本地 server)

统一信封:

```jsonc
{
  "type": "crash" | "error" | "event" | "perf",
  "ts": 1719100000000,
  "instanceId": "uuid",
  "version": "0.1.0",
  "platform": "win32",
  "sessionId": "可选",
  "payload": { /* 各类型字段 */ }
}
```

批量策略:

- 普通事件进内存队列,满 20 条或隔 10 秒 flush。
- `crash` 类立即 flush(进程可能马上退出)。
- **失败兜底 + 补传**:外发失败 → 落盘 `~/.<product>/logs/telemetry-buffer.jsonl`(每行一条)。任一次 flush 成功后,顺带读 buffer 补传积压,**补传成功即删除/截断该文件**(单次最多带 200 条,剩余下轮继续)。
- **防膨胀**:buffer 超 1MB 时丢弃较旧的一半,避免长期断网/地址错导致无限增长。
- 落盘文件**不是长期日志**,是「待补传队列」——成功上报后会被清空,正常情况下应为空或不存在。

### 6.2 上报后端:阿里云 SLS WebTracking

server flush 时把信封转成 SLS WebTracking 请求外发。**WebTracking 免 AccessKey 鉴权**,专为客户端打点设计,正好契合「地址走配置、无密钥」诉求。

**上报 URL**(完整 track URL 经环境变量注入,代码不写死):

```
https://{project}.{region-endpoint}/logstores/{logstore}/track

# 本项目实际地址(已确定):
https://localcoding.cn-beijing.log.aliyuncs.com/logstores/localcoding/track
#         └project┘ └──region:华北2·北京──┘            └logstore┘
```

> 配置方式:用单个环境变量 `APP_TELEMETRY_URL` 直接存上述完整 URL(而非拆三要素再拼),更不易出错。dev 态不设此变量;release 由打包/部署注入。server 启动读不到则视为「外发关闭」,仅本地落盘。

**POST 批量格式**(server 用此方式,一次发一批):

```jsonc
// Content-Type: application/json
{
  "__topic__": "telemetry",
  "__source__": "client",
  "__logs__": [
    { "type":"event", "name":"message_sent", "instanceId":"uuid",
      "version":"0.1.0", "platform":"win32", "ts":"1719100000000",
      "hasAttachment":"true" },
    { "type":"perf", "name":"app_startup", ... }
  ]
}
```

**关键约束**:

- `__logs__` 每个对象就是 SLS 一条日志;**所有字段值必须是字符串**(数字/布尔要 `String()` 转换),否则 track 接口报错。
- 信封的 `payload` 需**拍平**成顶层 key(SLS 是扁平 KV,不存嵌套对象),如 `payload.name` → `name`、`payload.attrs.hasAttachment` → `hasAttachment`。
- `__topic__` 用于区分数据类型(可按 `type` 设),便于查询时 `__topic__: event` 过滤。

### 6.3 可视化保障(对齐截图的查询/仪表盘)

要在 SLS 控制台像截图那样查询、聚合、出走势图,需:

1. logstore **开启 WebTracking 开关**(控制台 logstore 配置),否则 track 接口 403。
2. 为上报字段**建索引**(查询分析的前提):`instanceId`/`name`/`type`/`version`/`platform` 设为 text,数值类(如计数)设为 **long** 才能 SQL `SUM`/`count`。
3. 截图里 `__date__`/`__log_pattern__`/`__log_signature__` 是 SLS 日志聚类(LogReduce)自动字段,与本方案无关,不必关心。

### 6.4 安全提示(WebTracking 固有特性)

- WebTracking 免鉴权 = **任何人拿到 URL 都能往该 logstore 灌数据**(无法防刷/伪造)。这是该方案的固有取舍,适合非关键的统计打点;不要往这个 logstore 放任何敏感或需可信的数据。
- 上报 URL 只配置在 server 一处,不进前端 bundle(虽然免鉴权前端可直连,但仍走 server 中转以统一开关、补字段、落盘重试)。

### 6.5 开发期本地记录(不外发)

为便于开发期排查 telemetry 事件,server 端用 `isDevLogging()`(= 非真打包 `APP_IS_PACKAGED!=="1"`)作开关,把每条事件打到 server 日志(`[telemetry][type] {...}`),进 `~/.<product>/logs/server-YYYY-MM-DD.log`(需 `LOCALCLAW_LOG_FILE=1`)。

- **本地记录独立于外发**:`isDevLogging()` 与 `isRelease()` 解耦。
  - 纯 dev:`release:false` 不外发,但 `devLogging:true` → **只本地记录**。
  - dev + `APP_TELEMETRY_DEV=1`:两者皆 true → **本地记录 + 外发**(开发联调用)。
  - 真打包 release:`APP_IS_PACKAGED=1` → `devLogging:false` → **只外发,不写本地日志**(避免线上刷屏)。
- **前端联动**:`/api/app-info` 回传 `devLogging`,前端据此即使 `enabled=false` 也把事件 POST 到本地 server(由 server 决定记不记/外发不外发)。主进程上报本就无条件 POST,天然被记录。

## 7. 埋点清单(按运行时)

### 主进程 `electron/main.cjs`(已有 hook,扩展即可)

- `uncaughtException` / `unhandledRejection`(L373-378)→ crash
- `serverProcess.on("exit")` 异常退出码(L174)→ server 崩溃
- `did-fail-load` / `render-process-gone`(L270-275)→ 渲染崩溃
- 启动耗时:`waitForServer` 成功时间差 → perf

### Node server(NestJS)

- `main.ts` 全局 `uncaughtException`/`unhandledRejection`(L23-27)→ crash
- ~~全局 `ExceptionFilter` → HTTP 500 error~~ **本期不做**:全局 filter 会接管全站错误响应(改变既有 API 行为、SSE 流式接口可能双写),副作用大于收益;崩溃/错误大头已由主进程 + 前端 ErrorBoundary 覆盖。如需 server 5xx 监控,后续用更克制的旁路方式单独做。
- gateway/CLI spawn 耗时 → perf(**后置,本期不做**)

### 性能指标(本期范围)

- **仅做应用启动耗时**:主进程从 `app.whenReady` 到 `waitForServer` 成功 + 首窗 `did-finish-load` 的总时长,拆出 server 就绪、窗口加载两段 → perf。
- gateway 请求、CLI spawn 等其他性能指标本期不做,后续按需扩展。

### 前端 React

- 新增 `ErrorBoundary` 包裹 `AppShell`(当前 `frontend.tsx` 无 boundary)
- `window.onerror` / `onunhandledrejection` → error
- 行为埋点:启动、会话创建、关键功能点击 → event
- **消息发送埋点**(见 §7.1)→ event

### 7.1 核心使用指标:每日消息数 / 活跃设备数

**需求口径**(单机桌面应用):

- **每天发消息个数**:该设备当天从输入框发送给 agent 的消息条数。
- **每天发消息人数**:单机只有一个操作者,故「人数」= 当天有发送行为的**活跃设备数(distinct `instanceId`)= DAU**。设备去重在上报后端按 `instanceId` + 日期聚合,客户端只管上报「我发了一条」。

**埋点位置**:`packages/client/src/thread/Composer.tsx` 的 `handleSend`(L131)——这是输入框发送的唯一入口。

- 在「确实要发送」的判定之后埋点(`text` 或附件非空、真正派发时),**入队(running 时)和直发两条路径都要计**,避免漏计或重复计。
- 不计入:空内容回车、纯粹的停止/中断操作。

**上报事件**:

```jsonc
{
  "type": "event",
  "ts": 1719100000000,
  "instanceId": "uuid",
  "payload": {
    "name": "message_sent",
    "attrs": {
      "hasAttachment": true,    // 是否带附件(用于区分纯文本/富消息)
      "isFollowup": false       // 是否续聊入队(可选,便于分析使用模式)
    }
  }
}
```

> **不上报消息正文**(§8 隐私约束):只发计数信号与少量非敏感属性。

**后端聚合(SLS 查询语句示意,在 SLS 控制台/仪表盘执行)**:

```
# 每日消息数
__topic__: telemetry and name: message_sent
| select date_trunc('day', __time__) as day, count(*) as messages group by day order by day

# 每日活跃设备数(发消息人数)
__topic__: telemetry and name: message_sent
| select date_trunc('day', __time__) as day, approx_distinct(instanceId) as dau group by day order by day
```

> 前提:`name`、`instanceId` 已建索引(§6.3)。`__time__` 为 SLS 自动写入的服务端接收时间。

## 8. 隐私与安全

- 不上报源码内容、prompt 正文、API key、文件绝对路径。

## 10. 接口与数据契约

### 10.1 `GET /api/app-info`(前端兜底,external-server 用)

```jsonc
// 200
{
  "release": true,          // APP_IS_PACKAGED === "1"
  "version": "0.1.0",
  "platform": "win32",
  "instanceId": "uuid",     // 匿名设备 ID(来自 userData/telemetry-id.json)
  "telemetryEnabled": true  // 用户开关当前值
}
```

### 10.2 `POST /api/telemetry`(本地中转入口)

请求体为 §6 信封,或信封数组(批量)。server 行为:

1. `isRelease()` 为 false → 直接 204(dev 永不外发)。
2. `telemetryEnabled` 为 false → 直接 204(开关关闭)。
3. 否则补公共字段 → 入队/落盘 → 异步批量 POST 到线上接口。

### 10.3 `PUT /api/telemetry/consent`(开关写入)

```jsonc
{ "enabled": false }   // 写入 agent-settings.telemetry.enabled
```

### 10.4 preload 暴露(`window.electronAPI.appInfo`)

```js
// preload.cjs 新增,主进程经 ipcRenderer.invoke("app:info") 提供
appInfo: () => ipcRenderer.invoke("app:info")
// 返回 { release, version, platform, instanceId }
```

### 10.5 agent-settings 新增字段

```jsonc
// ~/.localclaw/settings.json
{
  "telemetry": {
    "enabled": true,    // 用户开关,release 默认 true
    "consentedAt": 0    // 首次知情提示确认时间戳,0=未提示
  }
}
```

> `AgentSettings` 为开放结构(`[key: string]: unknown`),直接加 `telemetry` 键即可,无需改 SDK 类型导出之外的逻辑。
> 设备 ID **不**存这里,统一落 `userData/telemetry-id.json`(§4),保持单一真相源。

## 11. 实施阶段(建议顺序)

每阶段独立可验证,dev 态全程零副作用。

1. **判别地基**:`main.cjs` 注入 env + `preload.appInfo` + `config/release.ts` + `GET /api/app-info`。验证:dev 拿到 `release:false`,装包拿到 `true`。
2. **设备 ID + 开关**:`electron/telemetry.cjs` 生成/持久化 ID;agent-settings `telemetry` 字段;`PUT /consent`。
3. **server 中转骨架**:`telemetry` 模块(controller + service),实现 `isRelease()`/开关双闸门 + 内存队列 + 落盘,**WebTracking 外发先留空打日志**(等 project/logstore 配置)。
4. **埋点接入**:主进程崩溃 hook → server 全局 ExceptionFilter → 前端 ErrorBoundary + 行为埋点。**核心使用指标 `message_sent`(§7.1)在本阶段接入**,优先级最高。
5. **设置 UI + 首启知情提示**。
6. **接上 SLS WebTracking**:注入 `APP_TELEMETRY_URL`;SLS 控制台开 WebTracking 开关 + 建索引(§6.3);打开真实外发,在控制台验证日志可查、可聚合出走势图。
